### #1 · 2026-08-04 · 자료 + 데이터베이스 준비

**뭘 시켰나**
```
일단 자료는 없는데 ... 기존 다 책으로 된 문서만 가지고 있다보니까 ...
일단 너가 데이터를 가져와서 만들어 줄 수 있어? HSK3급 신(3.0)으로 해서
뭐 전부다 가져올 필요는 없어 너 말대로 출퇴근 10분용으로 사용 할 수 있도록
만들면 좋겠따 ! (...) 지금은 일단 출퇴근 용 10분으로 테스트 베스 용으로 만들고
그 이후 데이터 검증, 정확성, 멱등성 이런거 다 확인 후 잘 동작하면 1시간 용으로 만들고..
```
```
아 그리고 이걸 저장할 데이터 베이스 만들고 테이블도 생성해야 하잖아
테이블 DDL도 같이 뽑아서 만들어줘 내가 supabase를 사용하는데
거기랑 연결해서 데이터 넣어두고 사용하도록 하면 될거 같아
```

**어떻게 됐나** — 한 번에 됨 (단어 100개 · DDL · 시드 SQL)

**몇 번 만에** — 1

**배운 것**
- **"자료가 없다"가 막힘이 아니었다.** 공식 목록은 이미 공개돼 있었고, AI가 찾아서 받아올 수 있었다. 진짜로 없는 건 목록이 아니라 **한국어 뜻과 예문**이었다.
- **AI가 기억으로 답하게 두면 안 되는 지점이 있었다.** "3급이 몇 단어인가"를 기억으로 쓰면 틀렸을 수 있는데, 실제 목록을 받아서 세니 973개였다. 숫자는 세는 게 맞다.
- **멱등성을 미리 말한 게 컸다.** 안 말했으면 `insert` 로 만들어졌을 거고, 4회차에 버튼 두 번째 누를 때 터졌을 것이다. 그리고 그때는 원인을 못 찾았을 것이다.
- 데이터에서 발견한 것 — 공식 목록에 **같은 한자가 두 번** 나온다 (把 개사/양사, 背 bēi/bèi). 한자를 기본 키로 잡았으면 단어가 에러 없이 조용히 사라졌다.

**시즌 2 문서 후보**
> 4회차 문서의 *"화면에서 클릭으로, SQL 안 씁니다"* 에 예외를 한 줄 붙일 것.
> 표가 2개 이상이거나 자료를 여러 번 다시 넣게 되는 아이디어는 **SQL 파일로 하는 편이 오히려 쉽다.**
> 클릭 업로드는 두 번 올리면 줄이 두 배가 되는데, 그걸 참가자가 알아채기 어렵다.

### #2 · 2026-08-04 · DB 생성 자동화 + 실제 적재

**뭘 시켰나**
```
이거를 내가 직접 하지 않고 너가 하게 할 순 없어? supabase랑 github랑 연동하면 되려나?
아니면 내가 지금 .env.local 파일을 만들고 url이랑 키를 넣으면
너가 만들어둔 sql을 가지고 DDL이 생성도 되고
그에 맞게 csv를 실행시켜 해당 테이블에 적재도 가능한게 만들고 싶어
```

**어떻게 됐나** — 됐음. `npm run db:all` 로 표 생성 → 단어 100개 적재 → 검증까지 자동

**몇 번 만에** — 1 (다만 접속 문자열을 찾는 데 한 번 헤맴)

**배운 것**
- **anon(publishable) 키로는 표를 못 만든다.** 표를 만들려면 DB 비밀번호가 들어간 접속 문자열이 따로 필요하다. 이걸 모르면 "키 넣었는데 왜 안 되지"에서 오래 막힌다.
- **Connect 화면에서 Session pooler 는 `Framework` 탭이 아니라 `Direct` 탭 안에 있다.** 이름과 위치가 안 맞아서 한 번 헤맸다.
- **자료를 CSV에서 바로 넣게 만든 게 컸다.** 이제 단어를 늘릴 때 SQL을 새로 만들 필요가 없다. `data/` 에 파일 놓고 `npm run db:seed` 하면 끝.

**실제로 확인한 것 (주장 말고 실행 결과)**

| 확인 | 결과 |
|---|---|
| 시드를 두 번 실행 | 100줄 그대로 (멱등 O) |
| `把`/`背` 같은 한자 중복 | 4줄 다 살아 있음 |
| 성조 없이 검색 (`baoan`) | `保安(bǎo'ān)` 찾힘 |
| 5번 클릭 시 진도 줄 수 | 1줄, `seen_count` 5 |
| `status` 에 한글 넣기 | check 제약에 막힘 |
| 없는 단어 가리키기 | 외래키 제약에 막힘 |

**★ 4회차에 반드시 터질 것을 미리 찾음**

> `progress` 를 `upsert` 로 저장해도 **`onConflict` 를 안 적으면 두 번째 클릭에 `409 duplicate key`** 가 난다.
>
> 기본 키는 `id`(자동 UUID)인데 겹침을 막는 건 `unique (user_key, word_id)` 라서, `onConflict` 가 없으면 Supabase가 기본 키를 기준으로 삼는다. `id` 는 매번 새로 만들어지니 안 겹치고, 결국 그냥 `insert` 처럼 굴다가 터진다.
>
> `{ onConflict: 'user_key,word_id' }` 를 적으면 `201 → 200 → 200`, 줄은 계속 1개.

**★ 내 검증 코드가 스스로 그 함정에 빠졌음**

권한 확인을 하면서 `204` 를 성공으로 읽었다. 실제로는 **"고칠 수 있는 줄이 0개"** 라는 뜻이었고 데이터는 그대로였다. 상태 코드만 보고 "권한이 안 걸렸다"고 판단할 뻔했다.

`site-notes.md` 에 이미 적어둔 그 교훈인데, **알고 있어도 또 걸렸다.** 이게 이 함정이 얼마나 잘 숨는지를 보여준다.

**시즌 2 문서 후보**
> 1. 4회차 문서에 **"저장이 됐는지는 응답 말고 데이터를 다시 읽어서 확인한다"** 를 실습 단계로 넣을 것. 글로만 적어두면 안 지켜진다.
> 2. `core/` 어딘가에 **"키 종류가 두 가지"** 를 한 문단. anon/publishable 키와 DB 비밀번호는 다른 것이고, 할 수 있는 일도 다르다.

### #3 · 2026-08-04 · 973단어 전체 적재

**뭘 시켰나**
```
앞으로 hsk3급 공부하면서 사용할 언어 필요한 언어 데이터들 다 적재 먼저 해두고
그러면 그에 맞게 이제 hsk3급 공부 할 수 있는 웹 사이트 만들어보자!
```

**어떻게 됐나** — 뼈대는 다 됨 (973개). 한국어 뜻은 100개까지

**몇 번 만에** — 4 (마이그레이션이 세 번 실패)

**배운 것**
- **"자료 다 적재" 가 한 가지 일이 아니었다.** 한자·병음·품사는 공식 목록에서 가져오면 끝인데, 한국어 뜻과 예문은 사람이 쓰는 일이라 시간 단위가 다르다. 이걸 한 덩어리로 보면 언제 끝나는지 알 수 없다.
- **표를 나눠둔 게 여기서 값을 했다.** `examples` 가 따로라 "한자는 있는데 예문은 아직" 인 상태가 자연스럽게 표현된다. 한 표였으면 빈 칸을 잔뜩 만들어야 했다.
- **영어 뜻은 근거로는 쓰되 믿으면 안 된다.** 사전에서 가져온 영어 뜻이 `白` 을 "surname Bai", `保` 를 "Bulgaria" 라고 한다. 첫 번째 뜻이 그 급수에서 쓰는 뜻이라는 보장이 없다. 그래서 화면에는 안 보여주고 `meaning_en` 에 참고용으로만 넣었다.
- **빈도 순위가 생겨서 "어떤 단어부터" 를 정할 수 있게 됐다.** 앞의 100개는 가나다순으로 잘랐는데, 실제로 공부할 거라면 자주 쓰는 것부터가 맞다.

**★ 마이그레이션이 세 번 실패했다 — 전부 같은 뿌리**

| 실패 | 에러 | 원인 |
|---|---|---|
| 1 | `cannot drop view v_words because other objects depend on it` | `daily_words` 가 보기를 반환해서 의존 |
| 2 | 같은 에러 | `search_words` 를 새로 만들었더니 또 |
| 3 | — | 딸린 걸 하나씩 나열하는 방식이 함수를 만들 때마다 깨짐 |

> **배운 것:** "몇 번 돌려도 되게 썼다" 고 생각했는데, **두 번째 실행에서만 드러나는 문제**가 있었다.
> 처음 만들 때는 지울 게 없어서 그냥 지나간다.
>
> 결국 `drop view ... cascade` 로 바꿨다. 보통은 위험한 선택이지만, 여기서는 매번 마이그레이션을 처음부터 전부 다시 실행하므로 딸려 지워진 것을 뒤쪽 마이그레이션이 다시 만든다.
>
> **되돌리기를 넣어둔 게 컸다.** 세 번 다 실패했지만 DB는 매번 실행 전 그대로였다. 안 넣었으면 반쯤 부서진 상태에서 원인을 찾아야 했다.

**★ 검색이 조용히 망가져 있었다**

`search_words('城市')` 를 하면 城市 가 아니라 **아무 단어나** 나왔다.

병음으로도 찾으려고 검색어에서 영문자만 남기는 처리를 했는데, 한자나 한글로 검색하면 남는 글자가 없어서 빈 문자열이 된다. `like '' || '%'` 는 `like '%'` 라서 **전부 일치**가 된다.

> **영문(`anpai`)으로 검색할 때만 멀쩡했다.** 내가 영어로만 테스트했으면 못 잡았을 것이다.
>
> 그래서 확인 스크립트의 기준을 **"결과가 나오는가" 에서 "엉뚱한 게 안 나오는가" 로** 바꿨다. 검색은 결과가 많이 나오는 게 오히려 고장의 증상이다.

**시즌 2 문서 후보**
> 1. 5회차(다듬기)에 **"검색을 만들면 반드시 한글·영문 둘 다로 쳐본다"** 를 한 줄. 한 종류로만 테스트하면 통과한다.
> 2. 확인이라는 말의 뜻을 다시 적을 것 — *"되는지 보는 것"* 이 아니라 *"안 되는 경우가 없는지 보는 것"*.

### #4 · 2026-08-04 · 사이트 만들기 (3회차 몫)

**뭘 시켰나**
```
너가 기획자 + 개발자 채용해서 PM이랑 소통하면서 사이트 만들어주면 돼!
반응형으로 만들어 PWA 형식으로 웹에서 볼 때 웹으로 모바일에서 볼 땐 모바일 형식으로 나오도록
HSK3급에 대한 문제도 너가 알아서 만들어주고 예상 문제들! 아닌가 이거까지는 필요없나?
일단 한자, 단어, 성조, 뜻 외우고 이 다음에 진행하도록 하면 되려나!
```

**어떻게 됐나** — 화면 4개 완성. 실제 브라우저로 확인까지

**몇 번 만에** — 3 (빌드 1번, 어두운 화면 버그 1번, 옛 서버가 남아 1번)

**배운 것**
- **"이거까지는 필요없나?" 하고 스스로 줄인 게 맞았다.** 문제은행을 지금 넣었으면 뜻도 안 외운 단어로 문제를 푸는 상태가 됐다. 범위를 줄이는 판단을 스스로 한 것이 이번의 제일 좋은 결정.
- **화면을 만드는 데 자료가 다 필요하지 않았다.** 200개로 만든 코드와 973개로 만들 코드가 같다. 자료를 다 채우고 시작했으면 오늘 사이트가 없었을 것이다.
- **폴더를 나눈 게 값을 했다.** `web/` 안에는 DB 비밀번호가 아예 없다. 나중에 Vercel에 통째로 올려도 걱정할 게 없다.

**★ 어두운 화면만 나오는 버그**

밝은 화면으로 요청했는데도 계속 어둡게 나왔다.

Tailwind v4 에서 `@theme` 을 `@media (prefers-color-scheme: dark)` **안에** 넣었기 때문이었다. `@theme` 은 미디어 쿼리 안에 있어도 통째로 끌어올려져서, 어두운 값이 밝은 값을 덮어썼다.

> 빌드된 CSS 를 열어보니 `--color-paper` 정의가 **하나뿐**이었다. 두 개여야 정상.
>
> **화면만 봤으면 "원래 이런 디자인인가" 하고 넘어갔을 것이다.** 나온 결과가 아니라 나온 코드를 봐야 잡히는 종류였다.

**★ 고쳤는데 화면이 그대로였다**

버그를 고치고 다시 빌드했는데 화면이 똑같았다. **아까 띄워둔 서버가 안 꺼지고 예전 빌드를 계속 주고 있었다.**

CSS 파일 이름이 아까와 똑같은 걸 보고 알아챘다. 파일 이름이 안 바뀌었다는 건 새 빌드가 아니라는 뜻이다.

> 이건 "고쳤는데 안 고쳐졌다" 로 오해하기 딱 좋다. 자칫 멀쩡한 코드를 또 고칠 뻔했다.

**시즌 2 문서 후보**
> 1. 5회차에 **"디자인을 고쳤는데 화면이 그대로면, 서버를 껐다 켜보기"** 를 한 줄. 참가자가 반드시 겪는다.
> 2. 6회차 배포 전 확인에 **"밝은 화면·어두운 화면 둘 다 열어보기"** 추가. 폰 설정에 따라 한쪽만 보게 된다.
